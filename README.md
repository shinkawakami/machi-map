# わが家の逃げ先

自宅・職場・実家といった**拠点ごと**に、**8種類の災害それぞれで使える最寄りの避難場所**を出す地図。

**https://wagaya-nigesaki.vercel.app/**

ログイン不要。登録も要りません。保存した拠点は URL に入るので、そのまま家族に送れて、
QR コードにして紙に出せます。

---

## このアプリが答える問い

> 自分の生活拠点から、**この災害のときに使える**最寄りはどこか。

避難場所を調べるきっかけは、引っ越し・防災の準備・ニュースを見たときなど、
ほとんどが平時で、そのとき知りたいのは**自分の生活範囲の中**です。
発災直後に「今いる場所から」調べる場面は、6つ数えたきっかけのうち1つしかありませんでした。
そこで、起点を「現在地」ではなく**登録した拠点**に置いています。

前提になる事実が2つあります。

**1. 避難場所は、災害の種類ごとに使える・使えないが分かれている。**
洪水では使えない避難場所があります。指定緊急避難場所には8種類の災害それぞれについて
指定の有無があり、たとえば地震で使えるのは 76.4%、火山現象では 9.3% です。

**2. 「指定緊急避難場所」と「指定避難所」は別物。**
前者は災害の危険から**緊急に逃げ込む**場所、後者は自宅に戻れなくなった人が**滞在する**場所です。
同じ場所が両方に指定されていることもあれば、片方だけのこともあります。

この2つを、表・地図・一覧・詳細のすべてで取り違えないように出すことを中心に置いています。

### 画面の作り

**1. 場所を決める。** 決め方は4つとも**常設**です。パネルの一番上が住所の検索、
その下に保存した拠点の★、地図の右上が「現在地」、そして地図を押す。
まだ決まっていないあいだは、パネルに**押せるものを2つだけ**出します
（「現在地から探す」「住所を入れる」）。以前ここは 11px の箇条書き4行で、しかも1つは
「地図の右上「現在地」を押す」と**画面の別の場所を指していました**。同じ重さの選択肢が
4つ並ぶのは推奨が無いのと同じで、初めて来た人はそこで止まります。
「住所を入れる」は上の欄に焦点を渡します（指すのではなく、そこへ連れていく）。
2回目以降は、開いた時点で拠点が起点になっているので、ここは飛ばせます。

**2. 8種の表を見る。** 拠点を選ぶと、災害8種それぞれの最寄りが1枚の表になります。
**行は8つではなく、行き先の数だけ並びます**（同じ施設に落ちた災害は1行に束ねる）。
逃げ先と呼べない距離のものは答えの欄に置かず、「近くにありません」として出します。
理由は「設計上の判断」の11。指定避難所の最寄りは、災害種別を持たないので**別枠**に置いています。

**3. 裏を取る。** 「近い順」タブで距離順の一覧、行を押すと詳細。
詳細では8種すべてを ○/× で出します（対応する災害だけを並べると、
「書かれていない災害はどうなのか」が読めないため）。
詳細からは**徒歩の経路を外部の地図アプリに渡せます**。ここが出せるのは直線距離までで、
川や崖を挟んでいても短く出ます。その先（どの道を通るか）は地図アプリの仕事なので、
座標を渡して開くだけのリンクにしています（API も鍵も使いません）。

**4. 持ち帰る。** 拠点は URL に入ります。コピーして家族に送るか、QR コードを表示するか、
`/print` で拠点ごとの表を紙に出せます。災害のときにスマホが使えるとは限らないので、
**紙に出ているほうが本来正しい**という考えです。

**操作は地図に重ねず、パネルに集めています。** 地図に残しているのは地図の一部
（起点のピン・現在地・件数）だけです。以前は「場所を決める」が中央のカード・下のバー・
左上のボタンに散っていて、同じ仕事なのに見る場所が毎回変わっていました。
パネルは狭い画面では下のシート、広い画面では左の柱になります。

地図を押したときの意味は、**避難場所の点が出ているかどうかで変えます**。
出ていない（範囲が広すぎる）うちは押した場所に寄るだけ、出てからは押した場所にピンを置く。
基準をズームの数字ではなく実際の件数に置いているので、**置ける状態なら必ず避難場所が見えています**。
置いたピンはドラッグで直せます（ずらしたいのはたいてい数十 m なので、
モードを切り替えて指し直させるより速い）。

全国19万件をクラスタにして出すのは**やめました**。画面が白い円で埋まって読めないうえ、
その円に覆われて地点を指すこともできません（最初はそう作って、実機で捨てています）。
いま開いた直後に出しているのは、避難場所が密にある**東京駅まわりを例として**寄せた画面です。
空の地図より、動いている画面を見せたほうが早い。例であることはパネル側で断っています。

**押せるものは 32px 以上、画面を切り替えるものは 36px 以上**にそろえています。
以前はタブや絞り込みのチップが実測 24px で、地図右上の現在地ボタンを 40px に
上げたときの基準（小さすぎる的をやめる）と食い違っていました。
**壊す操作は、押し分けの難易度を結果の重さに合わせます。** 拠点の★の隣にあった削除（✕）は、
いま見ている拠点にだけ出します。いちばんよく押す操作（切り替え）の隣に、同じ大きさで
壊す操作が常設されていたためです。同じ名前での保存（上書き）も、**一度止めて聞きます**
（削除には戻す帯があるのに、上書きには何もありませんでした）。

**入力欄は 16px を下回らせません。** これより小さい入力欄に触れると、iOS Safari は
ページごと拡大します（地図をピンチで拡大したいので、拡大そのものは禁止していません）。
住所の検索は **Enter と ↑↓ で完結**します。ただし**変換中のキーは IME のもの**なので、
横取りせずに先に逃がします（漢字を確定する Enter で候補が決まってしまうため）。

災害種別を選んでいる間も**指定避難所は絞り込みの対象外として残します**。
指定避難所には災害種別の指定がそもそも存在しない（元データに列が無い）ので、
黙って消すと「この災害で使える避難所が無い」と読めてしまい、黙って残すと
「この災害で使える避難所だ」と読めてしまいます。対象外である旨をフィルタ列に明示しています。

### データの限界（隠さず見せる）

このデータは「**市町村が登録し、かつ公開に同意したものに限る**」もので、全国を網羅していません。

市町村単位のカバー率は実測すると高く、1,747 市町村のうち両方公開が 1,691（96.8%）、
データ未登録は 21（うち6は北方領土なので実効的な空白は15市町村）でした。
一方で**市町村単位では公開されていても、施設単位で非公開のものがあり**、
これは件数で示すことができません（配布ページに明記されています）。

そのため、次の断りをフッタに置いています（狭い画面では1行に畳んでいて、開くと出ます。出典そのものは畳んだ状態でも残します。判断12）。

> 市町村が登録し公開に同意したものに限られ、最新でない場合や未掲載の場合があります。
> 実際の避難では必ず市町村の指示に従ってください。

そのうえで、公開状況そのものを
[データの公開状況](https://wagaya-nigesaki.vercel.app/coverage)（`/coverage`）でページにしています。
見せどころは「全国が埋まっていない」ではなく、**片方しか公開されていない35市町村**のほうです。
とくに指定避難所だけがある27市町村では、災害のときに最初に向かうべき指定緊急避難場所が
この地図に出てきません。数えられない施設単位の非公開についても、同じページで断っています。

近い順の検索でも、範囲内が0件になることは疎な地域では普通に起きます。
これを例外扱いせず、**半径を広げて近隣から返し、到達した半径を画面に出す**設計にしています
（データ未登録の奥多摩町でも、5.4km 先の御岳山ふれあいセンターを返します）。
ただし拠点ごとの8種の表では、**それを答えの欄には置きません**。逃げ先と呼べる距離（3km）を
超えたものは「近くにありません」として、どこにあるかだけを添えます（判断11）。

### ライセンス

国土地理院コンテンツ利用規約（公共データ利用規約 PDL1.0）。出典を記載すれば複製・編集・加工・商用利用が可能で、申請は不要です。背景地図の地理院タイルも同様です。
出典表示はフッタに常設し（狭い画面では権利者名と「もとに作成」の1行に畳み、開くと全文が出ます。判断12）、地図上にも MapLibre の AttributionControl で出しています。

```
出典：国土地理院ウェブサイト（指定緊急避難場所データ・指定避難所データ）をもとに作成
背景地図：地理院タイル
住所検索：「位置参照情報ダウンロードサービス」（国土交通省）をもとに作成
```

住所検索に使う位置参照情報も、出典を書けば申請なしで編集・加工できます
（位置参照情報利用約款）。加工しているので「をもとに作成」の形で書いています。

## 設計上の判断

作る前に決めず、**実測してから決めた**ものを残しています。数字はすべてローカルの
PostgreSQL（全国 199,116 件）での実測です。

### 1. 十数万点をどう地図に出すか

全件は返せません。選択肢は「bbox で絞る」「サーバー側でクラスタリング」「静的ベクタタイル
（PMTiles 等の事前生成）」の3つで、**bbox + 件数による自動切り替え**を採りました。

**ズームの閾値ではなく、bbox に実際に何件入っているかで切り替えます。**
2,000 件以下ならそのまま点を返し、超えたらグリッド集約したクラスタを返します。
ズームで切ると、過疎地では点で出せるはずの範囲までクラスタになり、都心では逆に破綻します。

往復は増やしません。`take: 2000 + 1` で1件多く取り、超過していたときだけ集約クエリに切り替えます。

| 表示範囲 | 範囲内の件数 | モード | 返した数 | 転送量 | API 応答 |
|---|---|---|---|---|---|
| z14 渋谷（徒歩圏） | 29 | points | 29 | 2.6KB | 14ms |
| z12 東京都心 | 936 | points | 936 | 83KB | 34ms |
| z10 東京都全域 | 10,330 | clusters | 167 | 7.2KB | 48ms |
| z8 関東 | 32,571 | clusters | 139 | 6.1KB | 55ms |
| z4 全国 | 199,116 | clusters | 27 | 1.3KB | 89ms |

**全国を出しても 1.3KB / 89ms。静的ベクタタイルは要らない**と判断しました。
「DB を叩く必要がないほど軽いから事前生成する」という理由で選ぶ案でしたが、
実際には DB を叩いても軽く、ビルド工程と配信先が増えるだけになります。

**ただし、この全国表示は入口から降ろしました**（下の判断7）。技術的には軽くても、
画面が白い円で埋まって読めず、地点を指す邪魔になります。クラスタは中ズーム以降で使っています。

グリッドのセルは `360 / 2^k` のはしごに丸めています。bbox の幅から素直に割ると、
パンのたびに丸め誤差でセル境界が動き、クラスタの点が小刻みに揺れます。
2の冪に固定すれば境界が地球に固定され、同じズームである限りパンしても動きません。

### 2. PostGIS を使わない

**Prisma が PostGIS の geometry 型に対応していません。**使うなら `Unsupported("geometry")` で逃がし、
地理検索はすべて `$queryRaw`、マイグレーションも手書き SQL になります。

緯度経度を Float 2列で持ち、矩形で絞ってから距離順に並べれば十分でした（上記・下記の実測）。
遅くなってから入れればよい、という順序で判断しています。

### 3. 災害種別の絞り込みを、どう索引で支えるか

**`(lat, lng)` の索引を `(lat, lng, kind, 災害種別8種)` の複合索引1本に置き換えました。**

クラスタ集約が読むのは `count` と `avg(lat)`, `avg(lng)` だけなので、
もともと **Index Only Scan** で完結していました。ここに災害種別の条件を足すと、
フラグを読むために heap へ行かねばならず、プランが Seq Scan に倒れます。
**索引にフラグを載せて Index Only Scan に戻す**のが答えでした。

| クエリ | 置き換え前 | 置き換え後 |
|---|---|---|
| z8 関東・絞り込みなし | 25.9ms | 20.6ms |
| z8 関東・洪水 | 60.0ms | 20.8ms |
| z8 関東・火山現象（緊急のみ） | 30.5ms | 4.8ms |
| z4 全国・洪水 | 82.0ms | 76.5ms |

- 索引サイズは 14MB → 9.6MB。元の `(lat, lng)` を置き換えるので**増えていません**
- z4（全国）では効きません。bbox が全件を含むので Seq Scan が正しく、索引で解く問題ではありません
- 災害種別ごとの部分索引8本も試しました。全国・火山現象で 27.0ms → 11.2ms と効きますが、
  複合索引1本で足りる範囲だったので採っていません
- Postgres の `INCLUDE` 列でも同じ効果・同じサイズでしたが、**Prisma のスキーマで表現できない**ため通常の複合索引にしました

### 4. 近い順の検索を、どこまで広げるか

**半径のはしごで倍々に広げます。** 2 → 4 → 8 → … → 256km。件数が揃った段で止め、
256km でも足りなければ「これ以上は見つかりません」と返します。

**矩形で絞ってから円で切り直す**のが要点です。矩形のまま距離順に並べると、角にある遠いものが入る一方で、
辺のすぐ外にあるより近いものが落ちます。円で切れば「半径内で最も近い N 件」になり、
N 件揃った時点で全体の最近傍だと言い切れます。
経度方向の幅は中心ではなく**矩形の端の緯度**で補正します（中心の緯度で割ると極側の角がはみ出します）。

| 地点 | 到達した半径 | 往復 | 最寄り | 応答 |
|---|---|---|---|---|
| 渋谷駅 | 2km | 1 | 313m 文化総合センター大和田 | 15ms |
| 渋谷駅・洪水（緊急のみ） | 4km | 2 | 1,122m 菅刈小学校及び菅刈公園 | 36ms |
| 渋谷駅・火山現象（緊急のみ） | 16km | 4 | 8,864m 中原中学校 | 41ms |
| 奥多摩町役場（データ未登録の町） | 16km | 4 | 5,438m 御岳山ふれあいセンター | 28ms |
| 南鳥島 | 256km（打ち切り） | 8 | 0件 | 26ms |

最初から半径 256km で1回引く案とも比べました（渋谷・SQL 単体）: **0.8ms 対 53.7ms**。
一発引きは Parallel Seq Scan になり、6万件に距離を計算させることになります。
都市部では1往復で終わるので、往復が増える心配より効きます。

### 5. スキーマは「施設」ではなく「指定」のリストとして持つ

**1テーブル + `kind` で種別を持ちます。**2つのデータセットを施設としてマージしていません。

共通IDは両データセットで重複が0件、突合できるのは「住所同一」フラグで 53.6% だけ、
突合できた側も「住所が同じ」であって同一施設とは限りません（施設名が一致するのは73%）。
施設としてマージしようとすると、**根拠のない同一視をアプリ側で作る**ことになります。
1行 = 1つの指定、として素直に持ち、公式のフラグをそのまま保持しています。

**災害種別8種は nullable にしています。** 指定避難所には災害種別が存在しないので、
Boolean で持つと `flood = false` が「洪水では使えない」なのか「そもそも指定がない」なのか
区別できません。避難場所を扱うアプリでこの2つを混同することは、間違った答えを出すことに直結します。

- `null` = 指定避難所なので、この災害種別の指定がない
- `false` = 指定緊急避難場所だが、この災害では使えない

`kind` があれば `null` かどうかは導けますが、**導けることと取り違えないことは別**で、コスト差はほぼありません。
なお「8種すべて非該当の指定緊急避難場所は0件」は実データで確認済みで、取り込みの検算に使っています。

### 6. 取り込みは毎回まるごと入れ替える

元データが公開されていて、いつでも取り直せます。差分更新のロジックを持つほうが高くつきます。
そのうえで、

- **3ファイルすべてをパースし終えてから**削除・投入に入る（壊れたデータで既存を消さないため）
- 検算3項目（災害種別が全 false の緊急避難場所=0 / 災害種別を持つ指定避難所=0 / 日本の範囲外の座標=0）。
  1つでも引っかかれば異常終了する
- ダウンロードは `.cache/gsi/` にキャッシュし、配布元に無駄なリクエストを投げない

元データには **UTF-8 BOM** が付き、**引用符の中に改行を含む行**があります（行分割で処理すると
200 件ほどずれます）。また全国 CSV は `_1` が指定避難所、`_2` が指定緊急避難場所で、
**番号と名前が直感と逆**です。

### 7. 入口で何を出すか（2回作り直している）

**一度目**は「開いた瞬間に全国19万件が載っている」ことを入口の差にしていました。
実機で見て捨てています。

- 全国ズームのクラスタは、画面が白い円で埋まるだけで読めない
- その円に覆われて、**地点を指すことすらできない**
- 「入力欄から始まらない」ことが効いているのであって、全件が載っていることではない

**二度目**は、その逆に振って「起点が決まるまで何も描かない」にしました。
地点の指し方も、タップ配置は**押した場所が指で隠れる**・**全国ビューから目的の街に当てられない**・
**パン操作と誤爆する**の3つを理由に、画面中央の十字に合わせて確定する方式へ変え、
拡大の手間は都道府県 → 市区町村ジャンプで消していました。これも捨てました。

- 何も描かない画面は、**白い円で埋まった画面と同じくらい「何のアプリか分からない」**。
  空白と過密のあいだを外しただけだった
- 十字は「地図から選ぶ」という**モード**を要求する。住所検索か現在地でその場所まで
  来ているのに、モードへ入ってそこでまた地名を選ばせるのは、同じ仕事の二重化だった
- 県・市区町村ジャンプは、そのモードを成り立たせるための部品で、
  住所検索（町丁目まで）が入った時点で存在理由が消えた

**いま**はこうしています。

- 開いた直後は、避難場所が密にある**東京駅まわりを例として**出す。空の地図ではなく、
  動いている画面を見せる。「なぜここ？」にならないよう、例であることはパネル側で断る
- 地図を押したときの意味は、**点が出ているかどうか**で変える。出ていなければ押した場所に寄り、
  出ていれば押した場所にピンを置く。**置ける状態なら必ず避難場所が見えている**
  （ズームの数字で切ると、件数しだいで「押せるのに何も見えない」が起きる）
- 誤差はドラッグで直す。ずらしたいのは数十 m なので、つまんで動かすほうが速い
- **押し間違いは元に戻せる。** 地図のタップはパンの終わりと見分けがつかず、当たると
  表が丸ごと入れ替わる。しかも移る前の起点が拠点でなければ（住所で指した地点など）、
  ★から戻ることもできない。移る前の起点と、見ていた面をそのまま戻す。
  戻す口を出すのは**地図のタップのときだけ**。住所・現在地・★は自分で選んだ操作で、
  取り消す前提で帯を出すと、そちらが邪魔になる
- 操作は地図に重ねず、パネルに集める。地図に残すのは地図の一部だけ

入口に点が出ているということは、**起点がまだ無い状態でも点が押される**ということです。
施設の詳細は起点に依存しないので、起点の有無に関係なく開くようにしています
（ここは一度、起点がある前提のまま点だけ先に出してしまい、押しても何も出ない状態を作りました）。

サーバー側の点／クラスタ切り替えそのものは残しています。あれは「広い範囲で3万点を返さない」
ための上限で、画面に描くかどうかとは別の話です。

### 8. 拠点は URL のフラグメントに置く（サーバーには持たない）

保存した拠点の正本は **URL**、localStorage はその写しです。

**Safari の ITP は「7日間そのサイトに触らないとスクリプトが書いたストレージを消す」**ため、
数か月おきに開く防災の題材では、クライアント保存を正本にする設計が成立しません。
一方サーバーに持てば、ログイン不要が崩れるうえ「自宅の位置」を預かる責任が生まれます。

```
https://wagaya-nigesaki.vercel.app/#s=自宅,35.6580,139.7016;職場,35.6812,139.7671
```

- **クエリ（`?s=`）ではなくフラグメント（`#s=`）。** クエリに入れると、共有された URL を
  開いた時点でリクエスト行に自宅の座標が載り、ホスティングのアクセスログに残ります。
  フラグメントはサーバーに送られません
- 座標は**小数4桁（約11m）に丸めます**。近い順は半径2kmから広げるので精度は足り、
  URL が短くなり、位置をそのままの精度で配らずに済みます
- 拠点名は**プリセット（自宅 / 職場 / 実家 / 学校）**を先に出します。自由入力だけにすると
  建物名や部屋番号が URL に入ります
- QR コードの生成も**クライアント側で完結**させています。サーバーに作らせると、
  その画像リクエストに座標が載るためです（URL 短縮を自前でやらないのと同じ理由）
- URL とこの端末の保存が食い違ったときは、**黙って上書きせず3択で聞きます**
  （入れ替える / 今回だけ見る / この端末のものを使う）

正本が URL と localStorage である以上、それは React の外にある状態なので、
`useSyncExternalStore` で読んでいます。

### 9. 「8種 × 最寄り」を1往復で引く

拠点の表は、災害8種＋指定避難所の**枠ごとに `UNION ALL` で「最寄り1件」**を引きます。

`DISTINCT ON` では書けません。1行が複数の災害に対応するので、
「洪水にも地震にも使える1件」を両方の枠に出す必要があります。
半径のはしご（判断4）はそのまま再利用し、**矩形内の最寄りが円の外なら円の中には何も無い**
という性質で、埋まらなかった枠だけ半径を上げて引き直します。

| 拠点 | 到達した半径 | 8種の充足 | 応答 |
|---|---|---|---|
| 渋谷駅 | 16km | 8/8 | 20ms |
| 札幌駅 | 32km | 8/8 | 40ms |
| 広島駅 | 32km | 8/8 | 20ms |
| 那覇市役所 | 4km | 8/8 | 20ms |

火山現象のように該当が 9.3% しかない災害で半径が伸びます。
埋まらなかった場合は「この付近に、この災害で使える指定がありません」と出します。

### 10. 住所検索は、外部 API ではなく自前の DB で解く

住所からの検索は、**使える規約の外部 API がほとんど無い**ところから設計が決まりました。

| 候補 | 判断 |
|---|---|
| Google Geocoding API | 結果を Google マップ上に表示する制約があり、地理院タイルに出した時点で違反 |
| Yahoo! ジオコーダ | 利用方法により有償版の申し込みが必要で、規約の判断が戻ってくる |
| 国土地理院 address-search | 公式回答が「主に地理院地図からの利用を想定」「長期的に提供できるとは限らない」 |
| Nominatim 公開エンドポイント | **オートコンプリート禁止**。住所入力の補助と正面から衝突する |

背景地図も避難場所データも公開された規約があるのに、住所検索だけ曖昧な依存を入れると、
**「公開してよいか」の判断がそこだけ戻ってきます**。このプロジェクトが避難場所を選んだ理由
（判断が要らないデータ）と矛盾するので、**国土交通省の位置参照情報を取り込んで自前で引く**
ことにしました。

- **番地は持ちません。** 答える問いは「近くのどこへ逃げるか」で、その先は近い順が半径2kmから
  広げます。町丁目の代表点と番地の差（数百 m）は最寄りの順位をほとんど変えません
- 表記ゆれの正規化（`lib/address.ts`）は、**取り込み側と検索側で同じ関数を通します**。
  片側だけ寄せると、ズレた瞬間に引けなくなります。実データで確認したゆれは、
  丁目の漢数字と算用数字の混在（漢数字 91,181 件に対し算用数字5件）、
  「大字」始まり 10,703 件・「字」始まり 8,007 件、`ケ` と `ヶ` の違いなど
- 検索は前方一致を3段（都道府県から / 市区町村から / 町名だけ）、最後に部分一致。
  人は「千代田区内幸町」のように**都道府県を省いて書く**ので、2段目が本命です

### 11. 「8種 × 最寄り」を、そのまま8行にしない

この表はこのアプリの答えそのものですが、**素直に8行出すと、いちばん見せたい差が消えます。**
指定避難所の位置を居住地の代わりに全国から300点サンプリングして、8種それぞれの最寄りを
引いて数えました。

| 8行に出てくる施設の数 | 割合 |
|---|---|
| **1施設（8行とも同じ名前）** | **35.7%** |
| 2施設以下 | 57.0% |
| 5施設以上 | 15.0% |

3人に1人は「同じ小学校が8回並んだ表」を受け取ることになります。
**同じ施設に落ちた災害は1行に束ね、違う行だけを立てます**（`lib/summary-view.ts`）。
8種すべてが1つに落ちたときは、名前を8つ並べずに「8種すべての災害」と書きます。

もうひとつ、**遠すぎるものを答えの顔で並べない**ようにしました。近い順の半径は
256km まで伸びるので（判断4）、その災害の指定が自分の市町村に無いと、遠くの市町村の
指定が最寄りとして返ります。同じ標本で最寄りまでの距離を測ると、

- 1km 以内に 66.6%、2km 以内に 72.1% がかたまる
- 3〜8km は薄い（7.1%）
- 8〜15km にもう一つの山（15.6%）

と割れます。後ろの山は「自分の市町村がその災害を指定していない」ぶんで、**答えではありません**。
実際、松本の座標で引くと高潮・津波の最寄りは **72km 先**でしたが、
これが 240m の松本城公園と同じ列・同じ書式で並んでいました。

谷が薄いので境目の数字は効きにくく、**徒歩で向かえるか**（3km でおよそ40分）を基準に
3km を採りました。これを超えた行は、名前を主役から降ろして「近くにありません」と言い切り、
どこにあるかだけを1行添えます（拾ったこと自体は隠しません。その災害の指定がどこにあるかは、
それはそれで知りたい情報なので）。**紙にも同じ規則で刷ります**。紙は戻って確かめられないぶん、
同じ名前が8回並ぶ表はなお読みにくく、間違った行は貼ったまま何年も嘘をつきます。

サーバー側（`lib/place-summary.ts`）は8行のまま返します。畳むのも遠さの判定も表示側の
仕事なので、API とキャッシュには手を入れていません。

### 12. フッタの全文を、地図から場所を借りない形にする

出典は規約上の義務なので消せません。**ただし「常設」と「全文を常に出す」は別の話です。**
全文は 11px で6行あり、iPhone 幅では**約 120px** を固定で取ります。ヘッダ（約 37px）と
合わせると、iPhone SE 相当（667px）では地図に使える高さが 506px まで落ち、そこへ下のシートが
65% 入るので、**見えている地図は 175px 前後**しか残りません。地図が主役の画面で、この配分は逆です。

そこで**権利者名と「もとに作成」の一行だけを常に見せ、残りを開いて読む形**にしました
（`<details>`。JS は要りません）。畳んだ状態でも3つのデータ源の権利者（国土地理院・国土交通省）は
名乗っていますし、背景地図の出典は地図右下の attribution にも常設で出ています。
地図まわりで広く使われている畳み方（`AttributionControl({ compact: true })`）と同じ姿勢です。

あわせて、シートの開閉を**隅の「▼」1文字から上端中央のつまみに変えました**。
下から出るシートのつまみはこの位置にあるものとして触られますし、記号1つぶんしかなかった的が
シートの幅いっぱいになります。畳んでいるときは見出しの行も押せるようにしてあります
（**畳んだシートを開けないのがいちばん困る**ので、開く側の的を大きく取る）。

### 13. 絞り込みは、効く先を言い、状態を地図に出す

絞り込みの操作はパネルの中にしかありませんが、**結果が出るのは地図**です。この差で2つ起きていました。

**1. 効かない画面の上に、断り書きが常設されていた。** 災害別の表は絞り込みを見ません
（8種すべてが並ぶこと自体が答えなので）。その理由を表の上に常設していたのですが、
既定は絞り込みなしなので、**誰も食い違っていない場面で全員がその2行を読む**ことになります。
断りは絞り込んでいるときだけ出し、代わりに**どこに効くのかを操作する場所で先に言う**
（災害種別を開いたときの「地図と「近い順」に効きます」）形にしました。

**2. 畳むと、絞り込んでいること自体が画面から消えていた。** 狭い画面でパネルを畳むと
絞り込みバーごと消えるので、点が減っている理由がどこにも出ません。そこで**状態を地図に出します**
（「洪水で絞り込み中」「避難所だけ表示中」）。絞り込み中は件数（「このあたりに N 件」）と
入れ替えます。件数はもともと判断に使われませんし、絞り込み中はその数字こそ説明を要するので。

**外す口は地図に置きません。** 地図に重ねるのは地図の一部（ピン・現在地・状態）だけで、
操作はパネルに集めるという整理をここで崩さない。状態さえ見えていれば、どこへ行けば
外せるかは分かります。

### 14. 紙の QR は、表示サイズではなくモジュールの実寸を固定する

拠点は URL に入るので、**拠点を増やすほど URL が伸び、QR が細かくなります。**
日本語の拠点名は percent-encode で1文字が9文字に膨らむため、効き方が急です。

| 拠点 | URL（percent-encode 後） | QR |
|---|---|---|
| 1件 | 73文字 | 37×37（型番5） |
| 3件 | 145文字 | 49×49（型番8） |
| 6件 | 289文字 | 69×69（型番13） |

印刷の QR は 104px（紙の上で 27.5mm）に固定していました。すると1モジュールの実寸は、
拠点1件の 0.611mm に対して**6件では 0.357mm** まで細ります。スマホでの読み取りは
0.4mm あたりが下限の目安なので、**拠点をたくさん登録した人だけが読めない紙を受け取る**
ことになっていました。しかも紙は刷り直しがきかず、読めないと分かるのは刷ったあとです。

そこで、固定するものを入れ替えました。**表示サイズは下限として扱い、1モジュールが
0.55mm を下回るときは自動で大きく描きます**（目安の 0.4mm に、家庭用プリンタの
にじみぶんの余裕を足した値）。読み取りを決めるのはピクセル数ではなく
モジュールの実寸なので、固定すべきはそちらでした。

| 拠点 | 変更前 | 変更後 |
|---|---|---|
| 1件 | 104px / 0.611mm | 104px / 0.611mm |
| 3件 | 104px / 0.483mm | 119px / 0.552mm |
| 6件 | 104px / 0.357mm | 161px / 0.553mm |

拡大にしか動かないので、拠点が少ないときの見た目は変わりません。画面の QR（168px）は
もともと下限を上回っていますし、そちらはピンチで拡大できるので、細くて困るのは紙だけです。
上の数字は幾何の計算ですが、**6拠点を入れた URL で実際に刷り、スマホで読めることを
確認しています**（余白・改ページも含めて問題なし）。

### 15. 災害種別の複数選択は AND にする

もとは単一選択で、理由は「**今この災害が起きたら**どこへ逃げるか」に対応させるため、と
コードに書いてありました。**その問いの立て方のほうを、先に降ろしています。**
調べるきっかけを6つ数えると5つは平時で、そのとき知りたいのは
「うちの拠点は、心配な災害の**どれでも**使える場所を持っているか」です。
単一選択は、降ろしたはずの発災直後の問いにだけ合わせた形でした。

複数選べるようにすると、掛け合わせの意味を決める必要があります。
**AND（選んだ災害の“すべて”で使える場所）**にしました。理由は2つで、2つ目は実測です。

**1. OR だと、地図の点の意味が読めなくなります。** 「洪水か地震のどちらかで使える」で
絞ると、画面に出ている点がどちらなのかは点からは分かりません。このアプリが見せたいのは
「災害の種類ごとに使える・使えないが分かれる」ことなので、その区別が消える出し方は採れません。
AND なら、出ている点はすべて「選んだ災害のどれでも使える場所」で、意味が1つに決まります。

**2. OR は、そもそも絞り込みとして機能しません。** z8 関東の矩形にある
指定緊急避難場所 18,887 件で実測しました。

| 条件 | 件数 | 残る割合 |
|---|---|---|
| 絞り込みなし | 18,887 | 100% |
| 洪水 | 13,073 | 69.2% |
| 洪水 **AND** 地震 | 11,385 | 60.3% |
| 洪水 AND 地震 AND 津波 | **2,104** | 11.1% |
| 同じ3種の **OR** | 18,434 | **97.6%** |

3種を OR で選んでも 97.6% が残ります。**選ぶほど画面が変わらなくなる操作**を、
絞り込みとして置く意味がありません。

**索引はそのまま効きます。** 同じ矩形で条件を増やして測ると、
3種の AND でも **Index Only Scan のまま・Heap Fetches 0**、読んだバッファは
557（絞り込みなし）→ 549（1種）→ 555（3種）とほとんど動きません。
災害種別8種を索引に載せた判断3が、そのまま複数条件にも効いています。

**クエリ文字列の並びは正規化します。** 絞り込みは URL に出て、CDN は URL をキーに
キャッシュします。押した順のまま載せると `flood,earthquake` と `earthquake,flood` が
別の URL になり、8種から選ぶ順列は最大 40,320 通りになります。データの列順に
並べ直してから載せることで、同じ絞り込みが同じ URL に落ちます
（bbox を格子に吸着させているのと同じ理由。判断1）。

**AND にしたことで、0件が普通に起きるようになりました。** 東京で「洪水 + 火山現象」を
選べば 0 件です。ところが絞り込み中は件数を出さない作りにしてある（判断13）ので、
そのままだと画面に残るのは「洪水・火山現象の両方で絞り込み中」だけになり、
**点が消えた地図を「まだ読み込んでいない」と読み分けられません。**
絞り込み中に限り「このあたりに該当なし」を出します。

## ローカルで動かす

```bash
docker compose up -d          # PostgreSQL 18（ホスト側 5434）
cp .env.example .env
npm ci                        # postinstall で prisma generate と MapLibre ワーカーのコピーが走る
npx prisma migrate deploy
npm run import:gsi            # 避難場所の取り込み。約60秒（--refresh で再ダウンロード）
npm run import:isj            # 住所検索用の町字データ。約30秒
npm run dev
```

- Prisma 7 の設定ファイルは **`prisma7.config.ts`**（`prisma.config.ts` ではありません）
- 生成物 `src/generated/prisma` は git に入れず、`postinstall` で再生成します
- MapLibre GL JS 6 のワーカーはバンドラの静的解析に引っかからないため、
  `postinstall` で `public/maplibre/` にコピーして `setWorkerUrl()` で自前配信しています
  （これを忘れると「地図は出るのに点だけ出ない」という症状になります）

## データの更新

**避難場所は月1回、住所（町字）は年1回。** どちらも差分は取らず、
**毎回まるごと入れ替える**（元データがいつでも取り直せるので、差分ロジックを持つほうが高くつく）。

### 避難場所（月1回）

```bash
set -a; . ./.env.neon; set +a    # 本番の接続文字列を読む（git には入れていない）
npx prisma migrate deploy        # スキーマを変えていれば当てる。無ければ何もしない
npm run import:gsi -- --refresh  # 取り直して入れ替える
```

- **`--refresh` を忘れない。** 付けないと `.cache/gsi/` に残っている前回の CSV を再利用するので、
  更新が入らないまま「成功」する
- ローカルの Docker を更新するときは、1行目を飛ばして同じコマンドを実行する
- 所要時間は本番（Neon / Singapore）で約90秒、ローカルで約60秒
- アプリ用は接続プーラー経由、マイグレーションは直結（`DIRECT_URL`）を使う。
  プーラー経由だとアドバイザリロックが効かない

### 住所の町字（年1回・版が上がったときだけ）

国土交通省の[位置参照情報](https://nlftp.mlit.go.jp/isj/)（大字・町丁目レベル）は年1回の更新で、
いまは **19.0b（2025年版）**を使っている。

```bash
# scripts/import-isj.ts の VERSION を新しい版に書き換えてから
npm run import:isj -- --refresh
```

- 版が上がったかどうかは配布ページで確認する。ファイルは
  `https://nlftp.mlit.go.jp/isj/dls/data/<版>/<都道府県コード2桁>000-<版>.zip` の形で並んでいて、
  **存在しない版は 404 を返す**ので、上げてみれば分かる
- 47都道府県ぶんを全部読んでから入れ替える（途中で落ちても既存を消さない）。
  検算は「47都道府県そろっているか」「日本の範囲外の座標が0か」「名前が空の行が0か」の3項目
- 所要時間はローカルで約30秒（zip 合計 3.2MB・191,106 件）
- 新しい版を入れたら、**検索の表記ゆれも見直す**。`lib/address.ts` の正規化は
  実データのゆれ（丁目の漢数字・「大字」始まり・`ケ`/`ヶ`）に合わせてあるので、
  データ側が変われば寄せ方も変わる

### 終わったら見るもの

避難場所の取り込みは、最後に検算と市町村の整備状況を出す。**3項目のどれかが0でなければ異常終了する。**

```
検算
  指定緊急避難場所                    115,829 件
  指定避難所                          83,287 件
  災害種別が全て false の緊急避難場所  0 件 (0 であること)
  災害種別を持つ指定避難所            0 件 (0 であること)
  日本の範囲外の座標                  0 件 (0 であること)
```

- **件数が前回と大きく動いていたら、原因を確かめてから終わりにする。** 元データ側で公開・非公開が
  変わったのか、取り込みが途中で壊れたのかは、件数だけでは区別がつかない
- 反映は [/coverage](https://wagaya-nigesaki.vercel.app/coverage) で確認できる。取り込み日、出典データの
  最終更新日、市町村ごとの公開状況が出る。このページはリクエストのたびに DB を引くので、
  データを入れ替えただけで反映される（デプロイし直す必要はない）
- 失敗した回は `ImportRun` に `FAILED` とエラーが残る

### 気をつけること

- **`Shelter.id` は取り込みのたびに変わる。** 外に出す識別子は共通ID（`sourceId`）なので、
  詳細ページの URL は入れ替えても壊れない
- 削除は `Shelter` → `Municipality` の順（逆にすると外部キーで落ちる）
- **入れ替え中の1分ほどは件数が0になる。** 無停止の切り替えはしていない。
  月1回・数十秒なので、そこに手間をかけていない
- Neon の Free プランは1ブランチ 512MB（全国データで108MB）。まるごとの入れ替えは WAL を生み、
  Neon はそれをストレージに数える（履歴保持は6時間なので、時間が経てば戻る）
